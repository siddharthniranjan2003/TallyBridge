Bottom line The most probable main cause is unbatched, computed whole-company report exports (P&L, Balance Sheet, Trial Balance) freezing TallyPrime's single UI thread — made worse because the client's 45 s timeout cannot cancel an in-progress computation, so the freeze outlives the sync. A secondary, less-frequent trigger is the on-demand push server on port 3002, which (unlike the queue poller) does not check whether a sync is running before hitting Tally.

1. The governing fact

TallyPrime's XML/HTTP gateway on port 9000 is single-threaded: it computes each request on the same thread that renders the UI. While a request is being computed, the Tally window is frozen. Everything below is a consequence of this one constraint.

There is also no server-side cancel — once Tally begins building a response, it runs to completion regardless of whether the caller is still listening.

2. Primary culprit — heavy unbatched exports saturating the UI thread

Mechanism. TallyBridge batches only the voucher fetch. fetch_vouchers_with_batches (sync_main.py:819) splits vouchers into month windows and recursively halves a window that times out. No other section has this protection. The following all issue a single whole-company request and wait for the entire result:

  • Reports — get_profit_and_loss, get_balance_sheet, get_trial_balance (tally_client.py:615–678)
  • Outstanding — get_outstanding_receivables / get_outstanding_payables (tally_client.py:573–610)
  • Masters — get_ledgers, get_stock_items, get_groups

Reports are the worst because they are computed statements — Tally must recalculate the entire period before returning a single byte, all on the UI thread.

Why it presents as "hangs sometimes" Severity scales with how much there is to compute, which varies by company size and day. The exports are gated by the sync plan (build_sync_plan, sync_main.py:369): masters fetch when masters changed; reports + outstanding fetch every time vouchers change; a full sync fires every heavy export at once. So a quiet day is fast, while month-end / a busy company / a first full sync freezes.

3. Aggravating factor — the client timeout can't stop Tally

The client read timeout defaults to 45 s (get_read_timeout_seconds, tally_client.py:32); the voucher-collection path bumps to 75 s, but reports and masters use the 45 s default.

When a heavy report exceeds 45 s:

  1. Python raises TallyTimeoutError and moves on / errors out.
  2. Tally keeps computing — there is no cancel.
  3. The Tally window stays frozen until the report finishes, after TallyBridge already walked away.
Net effect The freeze outlives the sync run and looks inexplicable from the operator's side: TallyBridge reports it gave up, yet Tally is still locked.

4. Secondary culprit — uncoordinated push path (concurrency gap)

Three independent components spawn Python that hits port 9000. Two of them coordinate with the sync engine; one does not.

CallerRoleCoordinates with sync?Evidence
SyncEngineRead (sync)Yes — one run at a timeactiveRunId guard, sync-engine.ts:188
PushQueuePollerWrite (queue, 5 s)Yes — before & between companiesisSyncInProgress(), push-queue-poller.ts:108–114
LocalPushServer :3002Write (on-demand)No — pushes immediatelyspawn on request, local-push-server.ts:200

A cloud-initiated push arriving on :3002 during a heavy export stacks a second request on the single-threaded gateway → a harder, more total freeze. Real, but less frequent — it only bites when a push coincides with a sync.

One-directional coordination The poller yields to the sync, but the sync does not check the poller (runAllCompanies only guards against another sync). So a narrow window exists where a sync timer fires while a poller push subprocess is still in flight. Much smaller than the :3002 gap, but not zero.

5. Non-code trigger (cannot be fixed in code)

TallyPrime's gateway only answers from a normal screen. If a modal dialog or data-entry screen is open in Tally — mid-voucher entry, a Yes/No prompt, a print or company-select dialog — Tally will not respond to any XML request until a human dismisses it. The caller then waits and hits the 45 s timeout — indistinguishable from a hang, but the cause is operational, not a bug.

7. Batched vs. unbatched: what fires when

SectionHow it's fetchedBatched?Fetched when
Vouchersmonth windows + split-on-timeoutYesvouchers changed
Groupsone requestNomasters changed
Ledgersone requestNomasters changed
Stockone request (+ summary fallback)Nomasters or vouchers changed
Outstandingone report export eachNovouchers changed
P&L / Balance Sheet / Trial Balanceone computed report eachNovouchers changed
Why only vouchers were batched Historical — vouchers were the section that actually crashed/hung the gateway, so that path was hardened (see the CHANGE 1–4 block and should_skip_voucher_family in sync_main.py). Masters could be batched (by name / master-id range) but weren't. Reports cannot be batched in the voucher sense — a Balance Sheet is one whole-period computation; the lever there is fetch-less-often / narrower-period / longer-timeout.

On a full sync (first sync, lost cache, backend has no alter-IDs, or forced) every heavy unbatched export runs at once — the worst case. On routine syncs you pay only for the sections that changed, but since reports re-run on any voucher change, that is most meaningful syncs.

9. Fastest confirmation (before writing code)

Look at one real hang in the logs and check the line immediately preceding the freeze:

  • Freeze right after [Metrics] profit_loss … / balance_sheet … / trial_balance …, or right when an idle/read timeout fires → §2/§3 confirmed (heavy exports).
  • Freeze coinciding with a [Push API] line from port 3002 → §4 confirmed (concurrency).

One log line likely settles which is dominant.
