The phrase logic converts raw OCR invoice text into structured search queries used to fuzzy-match against Tally stock item names in Supabase. It runs in four stages:

- **TOTEM**: fixes abbreviations (`ST SHK` â†’ `STRAIGHT SHANK`, `UNIF DISC` â†’ `UNIFIED DISC`)

### Stage 4 â€” Candidate Filtering + Scoring

After queries are built, matching proceeds through three filters before scoring:

**`candidate_rows_for_item`** (line 1334): Narrows the stock pool by:
1. `candidate_group_filter` â€” restricts to known group names per vendor (e.g., ET items only from group `"ET"`)
2. `candidate_vendor_tokens` â€” only rows whose name contains the vendor tag (e.g., `" ET"` in the name)

**`family_filter`** (line 1128): Structural gate â€” if the query contains `"DRILL"`, only candidates with `"DRILL"` in their name pass. Prevents a drill query from scoring against a tap candidate.

**`similarity_score`** (line 1237): Multi-factor score weighted across:
```python
sequence_score  * 0.15   # character-level SequenceMatcher
token_score     * 0.25   # token overlap (query tokens âˆ© candidate tokens)
numeric_score   * 0.35   # dominant â€” every number in query must match a number in candidate
fuzzy_score     * 0.10   # rapidfuzz token_set_ratio
rate_score      * 0.15   # invoice rate vs Supabase closing rate proximity
```
Numeric matching is weighted highest (0.35) because getting the size/pitch wrong is a hard failure even if the text looks similar. A bonus of +20 is added for exact normalized matches, +10 for substring containment.

**`best_query_score`** (line 1266): Runs all generated queries from Stage 3 against each candidate and takes the highest score â€” so if any one query formulation matches well, the item is accepted.

